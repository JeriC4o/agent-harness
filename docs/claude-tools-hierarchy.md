# Claude tools hierarchy

Embedded inventory of Tool / Subagent / Skill / Hook names. Consumed by `/ai-audit` Phase 2 Checklist O to detect clashes between project-defined names and Claude Code's embedded names.

> **AXIOM — Project-defined names MUST NOT clash with embedded names. On clash, the project name is renamed; the embedded name is never renamed.**

## §1a — Embedded Tools (built-in)

Names reserved by Claude Code's built-in tool set. Project-defined tool aliases that shadow these are forbidden.

- `Read`, `Write`, `Edit`, `Bash`, `Glob`, `Grep`, `WebFetch`, `WebSearch`
- `TaskCreate`, `TaskUpdate`, `TaskGet`, `TaskList`, `TaskOutput`, `TaskStop`
- `NotebookEdit`

## §1b — MCP servers (this project)

**None configured.** There is no project `.mcp.json`, so the harness exposes no `mcp__<server>__<tool>` tools. When a project adds one, enumerate its servers here — an MCP server name is as reserved as an embedded tool name, and a project-defined skill MUST NOT shadow one.

- PreToolUse(Bash) — `branch-protection`: blocks `git commit` / `git push` on the default branch, with the recovery recipe in its message **[guarded]**. **A branch DELETION is exempt, and the exemption keys on the TARGET, not on the verb** — `git push origin --delete <branch>` / `-d <branch>` / `:<branch>` sends nothing to the default branch. The exemption holds under **three** conditions, all of them necessary: the command is a LONE push (newlines are normalised to `;` first, and **any** `;` `&` `|` `` ` `` `$` in it disqualifies the exemption outright), it carries a deletion flag or is a colon-refspec deletion in the restricted form below, and the default branch's name does not appear in it as a whole word. **The two deletion spellings are NOT symmetric, and the difference is measured rather than assumed.** `--delete` / `-d` applies to EVERY refspec in the command, so such a push cannot also deliver a commit — `git push origin --delete feature-x HEAD` fails at rc=1 (`unable to delete 'HEAD'`) with the remote unmoved. A colon refspec applies only to itself, so one can ride beside a plain one: `git push origin HEAD :feature-x` deletes the branch AND fast-forwards the default branch, verified against a real remote. The colon form is therefore matched, anchored to the whole command, only when **EVERY refspec in it is a deletion** — a second refspec that is not itself a deletion disqualifies it, while several deletions together and flags in any position are fine. That last clause is not a convenience: `git push origin :a :b` is the shape this guard was filed over, and an earlier spelling of the anchor refused it, which would have shipped a guard that blocked its own originating command. Among push options, `--mirror` is the one to read twice — it is the only one that deletes remote refs AND delivers commits in a single call, so it is matched by neither deletion leg and stays blocked. The metacharacter condition is what makes the other two checkable: without it a deletion token belonging to a DIFFERENT sub-command exempted the whole string, so `git branch -d x && git push` passed while standing on the default branch — measured, and the reason the condition is spelled as a disqualifier rather than as a parse. Consequences worth knowing before reading a refusal: a deletion whose target is a variable or a substitution is blocked (its target genuinely cannot be read), a `cd <dir> && git push origin --delete x` prefix is blocked, and so is a deletion whose unrelated prose mentions the default branch. A refusal is therefore NOT evidence that the command would have pushed a commit

- PreToolUse(Bash) — `co-authored-by`: blocks a `Co-Authored-By` trailer in a `git commit` message (`-m` string or `-F` file) **[guarded]**

- PreToolUse(Bash) — `gate-pipe-guard`: blocks a gate — a named build / test / lint / format tool, **or a shell interpreter invoking a script file whose basename carries `test` / `check` / `lint` / `verify`**, **or `jq` carrying `-e` / `--exit-status`** (the flag that turns a parse into a verdict, which is what makes a manifest parse a gate — `jq` without it is an ordinary data read and is not matched), which is what makes a suite written in shell a gate rather than an ordinary command; a bare `bash -c …` is not one — whose result is MASKED — piped into `head`/`tail`/`grep`/`jq`/`sed`/`awk`/`wc`/`cut`/`sort`/`uniq`, fused to a trailing `|| echo` / `|| true`, **FOLLOWED across `;` by an `echo`/`printf` banner** (the next command replaces the gate's exit status — note the direction: a banner BEFORE a single gate masks nothing, because the gate is last, and is deliberately not matched), **joined to a SECOND shell gate with `&&`** (which leaves the first gate's verdict unreadable, and lets one legitimate non-zero truncate the rest of the chain). **That leg matches on its OWN pattern, not on the gate set above, and the difference runs both ways** — read it before concluding a conjunction is untouched: it requires a shell interpreter on BOTH sides, either carrying `-n` or running any `*.sh` / `*.bash` path, so it is WIDER than the gate set on the shell side (`bash -n a.sh && bash b.sh` is refused although neither side is a gate for any other leg — that spelling is the recorded incident this leg exists for) and NARROWER overall, since it admits no named build or test tool at all and therefore collides with no package-manager idiom. A conjunction of plain READS stays invisible by construction, which keeps that check with the author. Also, **redirected into `/dev/null`** (which discards the line naming WHICH assertion failed, so even a correct rc leaves nothing to act on), or **run inside a `for` / `while` loop** (which exits with the LAST iteration's status, erasing every earlier failure). The loop leg fires only when the loop BODY invokes a **named build / test / lint / format tool or a shell interpreter**, so a loop over `grep` / `awk` / `realpath` passes. **That is narrower than the rule on purpose, and a pass is not clearance:** `${CLAUDE_PLUGIN_ROOT}/docs/agents-method.md` § Tooling counts **search** among the gates, and blocking every loop containing a `grep` would be intolerable, so the hook deliberately under-approximates. The rule still binds on the construct. **A gate whose path arrives through a VARIABLE or a glob is invisible to this hook by construction** — no guard that matches the command string can see it — so that construct check stays with the author. Carve-outs pass: a `cd <dir> &&` prefix, a `[ -n … ] &&` guard that does not swallow the rc, and any chain inside a hook or checked-in `.sh`. **The gate match is anchored at COMMAND POSITION** (start of string, or after `;` `&` `|` `(` `` ` ``), so a gate name inside a search pattern — the project's own propagation sweep — is not a gate invocation and is not blocked. Newlines are normalised to `;` before matching, so a gate piped across a line break is still caught, and **redirections (`2>&1`, `&>`) are normalised away**, so the commonest spelling of a piped gate no longer slips past the `&` the gap cannot cross. There is NO heredoc opt-out: prose that quotes a piped gate at the start of a line is blocked like any other, and the remedy is the `Edit` / `Write` tools per `${CLAUDE_PLUGIN_ROOT}/docs/workflow.md § Hook false-positive guard`
- PreToolUse(*) — `loop-index`: appends one line per tool call to a per-session ledger (`~/.claude/harness/loops/<session_id>.jsonl`) and, when the SAME `hash(tool + arguments)` has already run within the last `HARNESS_LOOP_TAIL` **CALLS** (default 20), returns `permissionDecision: "ask"` with the count. **The unit is load-bearing and the word "steps" is retired from these messages:** the window is a count of `kind: "call"` ROWS, bound inside `${CLAUDE_PLUGIN_ROOT}/hooks/lib/loop-window.awk`, where the shell can only bound a tail by LINES — and once `loop-result` began writing a row per call, a 20-line tail was roughly 8 calls while the message still said 20. The agent is now told the span actually counted plus the call being judged, never the setting; the verdict row keeps the setting under `window` and names its unit in `window_unit`, because rows written before this change counted lines and nothing in the number separates them. **The intervening-edits filter is CONDITIONAL on the outcome**, and that is not a nicety: for calls that succeeded, a write between the repeats means the world changed and the finding is dismissed; for calls that FAILED, the edit means an attempt was made and the call failed again — the fix-break cycle, where dismissing it is how the commonest logical loop stayed invisible. Two prior failures fire as `error-retry`; three occurrences fire as `loop`. Both numbers mirror `${CLAUDE_PLUGIN_ROOT}/scripts/session-events.sh` (`retry_min: 2` against `minrep: 3`), which applies the same split per signature and always did — the live index diverged from it until GH-69. The key is the **hash alone** and `agent_id` is a field beside it — putting the agent in the key would stop the same hash from two agents matching, which is the fan-out case (N siblings each doing one identical call) that no per-agent view can see. **That arm fires on a ledger this build writes:** `agent_id` is taken straight from the PreToolUse payload, which carries it on a call made inside a subagent and omits it on the main agent's own calls, so an omission stores `main` and a malformed value degrades to `main` rather than dropping the row. **That degradation is silent by construction and the `agent-mark` row below is the only thing that makes it visible** — a stored `main` is indistinguishable from a genuine main-agent call, which is how ten of twelve field ledgers recorded every subagent as `main` with every count beside it correct. The ledger is an **index, not a copy**: it stores `tool_use_id` and the transcript path, so detail is one join away and no argument content is duplicated; `transcript` is per entry because a subagent writes its own file. The fingerprint is the same djb2 as `${CLAUDE_PLUGIN_ROOT}/scripts/session-events.sh`, and the two must not drift. **`ask` routes into the normal permission flow, so an already-allow-listed command can pass through without a prompt** — the stderr line is the half that always lands. - Stop, SubagentStop — `loop-verdict`: the COARSE stage of the cascade (exact hash → coarse hash → model → deep analysis). Writes a `kind: "turn"` marker on every stop — the ledger has no turn index because `PreToolUse` does not know one, and `Stop` IS the turn boundary — then fires when ONE `bin` repeats `min_bin_repeats` times **within that turn**. The bin comes from `${CLAUDE_PLUGIN_ROOT}/scripts/bin-of.jq`. **The gate is deliberately not a tier-1 signal**: tier 1 fires only on byte-identity, so gating on it would confine this stage to the class tier 1 already caught. **Its first design did not discriminate and was replaced from measurement:** counting DISTINCT fingerprints and requiring one tool to dominate fired on healthy work every time, because ordinary varied work is also "all fingerprints distinct", and in a shell-driven session one tool is ~98% of calls so concentration is vacuous. Coarse repeats within a turn gave a spread (11 / 5 / 4 / 3 / 2) where both older figures were identical for every turn. **The model stage is OFF by default** (`HARNESS_T3_MODEL`); when on it writes a separate `tier: 3` verdict and takes its reason from the FIRST line of the answer. That row also records `flagged_calls` and `unresolved_calls` — how many calls the stage was asked to judge and how many of those yielded no transcript text, so a reader can weigh a verdict by the evidence it rested on; a stored transcript that exists without the call's `tool_use_id` in it counts as unresolved exactly as an absent file does. **It never blocks** — a `Stop` hook returning exit 2 forces the conversation to continue, which is the failure this detector exists to catch. Turn scoping makes re-judging impossible by construction. Absent `claude`, a failed call or an unparseable answer all end it silently. Narrower trigger, same mechanism, and once per TURN rather than once per call
- SubagentStart — `loop-agent-mark`: appends one `kind: "agent-mark"` row per subagent spawn, carrying `agent_id` and `agent_type`, into the same per-session ledger (`SubagentStart` delivers the PARENT `session_id`, which is the key `loop-index` uses, so the mark lands in the file the call rows are in — measured, not assumed). **It is a CANARY and not a second source of attribution**, which is the distinction that decides what may be built on it: `PreToolUse` already supplies a real `agent_id` on the current build, so this improves attribution by nothing at all. What it buys is that "N subagents started, zero non-`main` call rows" becomes a self-contradiction detectable from the ledger alone, where today the degradation at `loop-index`'s `agent_id` read is indistinguishable from a genuine main-agent call. **It needs a COUNT of starts, not an identity, and no reader may join an `agent-mark` row to a `call` row** — that join is read-time attribution, which `loop-metrics.sh --for` already does by the only honest route, a transcript scan. **It closes one direction only:** zero recorded starts cannot separate "no subagent ran" from "this hook is not firing", and both readers print that bound rather than implying coverage they do not have. The event structurally **cannot block a spawn** — its `hookSpecificOutput` carries only `additionalContext`, with no `permissionDecision` — but a non-zero exit still becomes a `hook_blocking_error` attachment, so the exit-0 discipline binds exactly as it does on the other ledger writers — including their one exception. **The script may not be called `subagent-start.sh`**: a hook command must not name itself with a reserved event-name word from §3b, and that is the forbidden spelling. Unguarded; **every failure path exits 0, unconditionally — but silence is the default rather than the guarantee**, the unwritable ledger being the one deliberate exception, per the ledger-write bullet below
- **An unwritable ledger is the ONE failure these hooks do not swallow**, and the asymmetry is deliberate. Every other failure path exits 0 in silence because it costs a single row; an unwritable ledger disables tier 1 and tier 2 for the whole session while every tool call still succeeds and nothing looks wrong, which is the failure class the cascade exists to catch. So `${CLAUDE_PLUGIN_ROOT}/hooks/lib/ledger-write.sh` — sourced by `loop-index`, `loop-result`, `loop-agent-mark` and `loop-verdict`, and the single place the rule lives — reports it **once per session**, as one sentence on stderr naming the path and the consequence. It detects a failed OPEN *and* a failed WRITE, because a successful open followed by a failed write returns non-zero with nothing on stderr and an open-only check is an alarm for one mode out of several. The once-marker is a `mkdir` under `TMPDIR` keyed by a sanitised session id — not beside the ledger, which is the unwritable thing — and an unwritable `TMPDIR` degrades to silence rather than to a warning per call. It still never exits non-zero and never emits a `permissionDecision`. **A scratch-file write is NOT in this class** (`loop-verdict`'s tier-3 detail file): it costs tier 3 one turn, the existing guard degrades to a turn marker, and the ledger a reader inspects is intact, so it is quiet like the five other degradations beside it
- **The ledger carries five record classes** — `kind: "call"` (one per tool call), `"result"` (one per outcome), `"turn"` (one per stop), `"verdict"` (one per firing) and `"agent-mark"` (one per subagent spawn) — and **every reader MUST filter on `kind` BY NAME**: a verdict line carries `tool` and `fp` exactly like a call, so counting one lets each firing make the next more likely. Strict naming rather than exclusion is what made the canary free: `loop-window.awk` admits `call` and nothing else, so a new class cannot enter a window or a count without someone deciding it should. `tier` separates a hash catch from a model catch; `window` / `threshold` record the settings in force, without which a later reader cannot tell a wrong call from a since-changed setting. **Outcome is never written** — a hook cannot see its own effect, but the observations that follow a verdict are the outcome: the same `fp` again means the call went ahead, its absence means it was abandoned, a different `fp` on the same tool means it was reformulated. A call also records `cwd`, because **the ledger is global — one directory for every project — and rates are never pooled across them**: thresholds that fit one codebase say nothing about another, and a mixed figure lets one busy project set a number that reads as general. The project is technically recoverable from the transcript path, whose directory encodes it by replacing `/` with `-`, but that encoding is lossy where a directory name contains a hyphen, so `cwd` is stored exact and the recovered form is a fallback the report labels as such. `${CLAUDE_PLUGIN_ROOT}/scripts/loop-metrics.sh` is what derives all of it, grouping by project and reading outcomes by **position rather than timestamp** — a verdict is appended right after the call that triggered it, so at one-second resolution the two share a `ts` and a time-keyed read readmits the trigger, reporting every verdict as went-ahead. **A tier-2 decline is recorded too** (`verdict: "progress"`), which is not a reversal of "non-firings are not logged": for tier 1 every call is a line, so an absent adjacent verdict IS the non-firing, while for tier 2 the gate firing is itself unrecorded. Recording it both suppresses re-asking the model about a window it already declined and makes the structural gate's false-positive rate countable
- **`loop-metrics.sh --for <transcript.jsonl>` is the ledger view `/inspect` reads**, and it takes a TRANSCRIPT because that is all the skill holds. It resolves the session id from the path — with a special arm for a subagent transcript, `<session-id>/subagents/agent-<id>.jsonl`, whose basename is the agent and would otherwise resolve to a ledger no session ever writes. It emits the verdicts with the fields that make one **locatable** in the run (`ts`, `bin`, `repeats`, `count`, the threshold it fired under, the model's `reason`) rather than merely countable, plus a per-agent census recovered by `tool_use_id`. **A ledger that is absent is emitted as `available: false` with a reason, at rc 0**, so it joins the `unavailable` list rather than reading as a clean run — while an absent TRANSCRIPT stops the run at rc 2, because attribution is a lookup in that file and losing it does not degrade the census but makes every call unattributed beside counts that stay correct. `attribution.complete` is a four-way conjunction, each leg something the reader executed — the main transcript was opened, nothing failed to parse, every agent the ledger names had its transcript opened (`every_stored_agent_read`, with `stored_agents_unread` naming the ones it did not), and no unattributed call sits where a call still executing cannot be (`unattributed_at_tail`) — and **is not a guarantee that attribution succeeded**: the ledger names only the agents that made a call, so a subagent transcript that is simply absent while its calls happen to be last stays invisible. `attribution.agreement` reports the stored ids against the recovered ones as `checked` / `confirmed` / `refuted`, with up to five `refutations` carrying `tool_use_id`, `stored` and `recovered`. **A reader checks `complete` before reading `unattributed`,** and treats a large `unattributed` as worth reporting even when `complete` is true. **Join a ledger row to the transcript by `tool_use_id`, never by fingerprint:** the two are computed from the hook payload and from the recorded call, and they disagree for tools whose input the client rewrites in between (`Agent`, `AskUserQuestion`) — which is exactly the tool a fan-out question is about
