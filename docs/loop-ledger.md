# The loop ledger

What the loop-detection hooks write, extracted from
`${CLAUDE_PLUGIN_ROOT}/docs/claude-tools-hierarchy.md` § Project-defined Hooks, which keeps the hook
inventory and points here. That page exists to enumerate NAMES for clash detection; these four
paragraphs describe the ledger's contract instead, and are needed when a ledger row is written or read
rather than when a name is checked.

## The loop ledger

- **An unwritable ledger is the ONE failure these hooks do not swallow**, and the asymmetry is deliberate. Every other failure path exits 0 in silence because it costs a single row; an unwritable ledger disables tier 1 and tier 2 for the whole session while every tool call still succeeds and nothing looks wrong, which is the failure class the cascade exists to catch. So `${CLAUDE_PLUGIN_ROOT}/hooks/lib/ledger-write.sh` — sourced by `loop-index`, `loop-result`, `loop-agent-mark`, `loop-verdict` and `gate-record`, and the single place the rule lives — reports it **once per session**, as one sentence on stderr naming the path and the consequence. It detects a failed OPEN *and* a failed WRITE, because a successful open followed by a failed write returns non-zero with nothing on stderr and an open-only check is an alarm for one mode out of several. The once-marker is a `mkdir` under `TMPDIR` keyed by a sanitised session id — not beside the ledger, which is the unwritable thing — and an unwritable `TMPDIR` degrades to silence rather than to a warning per call. It still never exits non-zero and never emits a `permissionDecision`. **A scratch-file write is NOT in this class** (`loop-verdict`'s tier-3 detail file): it costs tier 3 one turn, the existing guard degrades to a turn marker, and the ledger a reader inspects is intact, so it is quiet like the five other degradations beside it
- **The ledger carries six record classes** — `kind: "call"` (one per tool call), `"result"` (one per outcome), `"turn"` (one per stop), `"verdict"` (one per firing), `"agent-mark"` (one per subagent spawn) and `"gate"` (one per covered gate run, below) — and **every reader MUST filter on `kind` BY NAME**: a verdict line carries `tool` and `fp` exactly like a call, so counting one lets each firing make the next more likely. Strict naming rather than exclusion is what made the canary free: `loop-window.awk` admits `call` and nothing else, so a new class cannot enter a window or a count without someone deciding it should. `tier` separates a hash catch from a model catch; `window` / `threshold` record the settings in force, without which a later reader cannot tell a wrong call from a since-changed setting. **Outcome is never written** — a hook cannot see its own effect, but the observations that follow a verdict are the outcome: the same `fp` again means the call went ahead, its absence means it was abandoned, a different `fp` on the same tool means it was reformulated. A call also records `cwd`, because **the ledger is global — one directory for every project — and rates are never pooled across them**: thresholds that fit one codebase say nothing about another, and a mixed figure lets one busy project set a number that reads as general. The project is technically recoverable from the transcript path, whose directory encodes it by replacing `/` with `-`, but that encoding is lossy where a directory name contains a hyphen, so `cwd` is stored exact and the recovered form is a fallback the report labels as such. `${CLAUDE_PLUGIN_ROOT}/scripts/loop-metrics.sh` is what derives all of it, grouping by project and reading outcomes by **position rather than timestamp** — a verdict is appended right after the call that triggered it, so at one-second resolution the two share a `ts` and a time-keyed read readmits the trigger, reporting every verdict as went-ahead. **A tier-2 decline is recorded too** (`verdict: "progress"`), which is not a reversal of "non-firings are not logged": for tier 1 every call is a line, so an absent adjacent verdict IS the non-firing, while for tier 2 the gate firing is itself unrecorded. Recording it both suppresses re-asking the model about a window it already declined and makes the structural gate's false-positive rate countable
- **A `kind: "gate"` row is one covered gate run** — a segment of a Bash command that the shared gate vocabulary `${CLAUDE_PLUGIN_ROOT}/hooks/lib/gate-pattern.sh` matches, or a checked-in script carrying `test` / `check` / `lint` / `verify` in its path executed directly. It carries `gate` (the script path relative to the repository or the plugin, or the tool and its first word), `args` (every argument, classed `file:<path>@<content hash>`, `dir:<path>`, `sel:<value>` for the project's declared selection flag, or `mode:<word>`), `artefact` (the file, directory and selection arguments alone), `repo`, `digest` (`${CLAUDE_PLUGIN_ROOT}/scripts/tree-digest.sh` at the repository top, `null` outside one), `ok` (`true` / `false`, or `null` where the exit status cannot be attributed to that gate), `agent_id`, `tool_use_id`, `cwd`, `command`, and `signal`. **Two signals, both blocking nothing:** a `repeat` is an earlier row with the same `gate`, `args` and `digest`; a `contradiction` is one with the same `gate`, `artefact` and `digest` and the opposite non-null `ok`, and wins when both apply. Either is matched against every earlier gate row of the session in the same repository, whatever agent wrote it, and adds `prior_tool_use_id`, `prior_ts` and `prior_agent_id`. Equal digests are the tree-unchanged condition, so fail, fix, pass is silent; a null `ok` takes part in repeats and never in contradictions
- **`loop-metrics.sh --for <transcript.jsonl>` is the ledger view `/inspect` reads**, and it takes a TRANSCRIPT because that is all the skill holds. It resolves the session id from the path — with a special arm for a subagent transcript, `<session-id>/subagents/agent-<id>.jsonl`, whose basename is the agent and would otherwise resolve to a ledger no session ever writes. It emits the verdicts with the fields that make one **locatable** in the run (`ts`, `bin`, `repeats`, `count`, the threshold it fired under, the model's `reason`) rather than merely countable, plus a per-agent census recovered by `tool_use_id`. **A ledger that is absent is emitted as `available: false` with a reason, at rc 0**, so it joins the `unavailable` list rather than reading as a clean run — while an absent TRANSCRIPT stops the run at rc 2, because attribution is a lookup in that file and losing it does not degrade the census but makes every call unattributed beside counts that stay correct. `attribution.complete` is a four-way conjunction, each leg something the reader executed — the main transcript was opened, nothing failed to parse, every agent the ledger names had its transcript opened (`every_stored_agent_read`, with `stored_agents_unread` naming the ones it did not), and no unattributed call sits where a call still executing cannot be (`unattributed_at_tail`) — and **is not a guarantee that attribution succeeded**: the ledger names only the agents that made a call, so a subagent transcript that is simply absent while its calls happen to be last stays invisible. `attribution.agreement` reports the stored ids against the recovered ones as `checked` / `confirmed` / `refuted`, with up to five `refutations` carrying `tool_use_id`, `stored` and `recovered`. **A reader checks `complete` before reading `unattributed`,** and treats a large `unattributed` as worth reporting even when `complete` is true. **Join a ledger row to the transcript by `tool_use_id`, never by fingerprint:** the two are computed from the hook payload and from the recorded call, and they disagree for tools whose input the client rewrites in between (`Agent`, `AskUserQuestion`) — which is exactly the tool a fan-out question is about
