# Project-defined hooks — the inventory

Extracted from `${CLAUDE_PLUGIN_ROOT}/docs/claude-tools-hierarchy.md` § Project-defined Hooks, which keeps
the index of names and points here for each hook's behaviour. The index stays there because that page is
where a name clash is detected and where both surfaces are compared; the bodies live here because four
fifths of that page was this one list, and a page loaded for a name check should not carry every hook's
reasoning with it.

**Read this page when a hook's behaviour matters** — what it matches, what it deliberately does not,
where it fails open, and which of its bounds are measured rather than assumed. Every bullet below is the
hook's contract in the vocabulary of what it does at dispatch, not of how it is registered: the
registration is in `${CLAUDE_PLUGIN_ROOT}/hooks/hooks.json`, which is the authority on whether a hook is
wired at all.

## The hooks

Defined in `${CLAUDE_PLUGIN_ROOT}/hooks/hooks.json`. A hook marked **[guarded]** is prefixed with
`"${CLAUDE_PLUGIN_ROOT}"/hooks/lib/harness-managed.sh || exit 0` and no-ops in a repo with no harness
profile (no `ai-docs/` and no `AGENTS.md`) — it presupposes that profile. An unmarked hook encodes pure
method and holds in every repo, which is why it carries no guard.

- SessionStart — rules-load reminder **[guarded]**
- PreToolUse(Bash) — broad `find` / `grep -r` over `$HOME` blocker
- PreToolUse(Bash) — `branch-protection`: blocks `git commit` / `git push` on the default branch, with the recovery recipe in its message **[guarded]**. **A branch DELETION is exempt, and the exemption keys on the TARGET, not on the verb** — `git push origin --delete <branch>` / `-d <branch>` / `:<branch>` sends nothing to the default branch. The exemption holds under **three** conditions, all of them necessary: the command is a LONE push (newlines are normalised to `;` first, and **any** `;` `&` `|` `` ` `` `$` in it disqualifies the exemption outright), it carries a deletion flag or is a colon-refspec deletion in the restricted form below, and the default branch's name does not appear in it as a whole word. **The two deletion spellings are NOT symmetric, and the difference is measured rather than assumed.** `--delete` / `-d` applies to EVERY refspec in the command, so such a push cannot also deliver a commit — `git push origin --delete feature-x HEAD` fails at rc=1 (`unable to delete 'HEAD'`) with the remote unmoved. A colon refspec applies only to itself, so one can ride beside a plain one: `git push origin HEAD :feature-x` deletes the branch AND fast-forwards the default branch, verified against a real remote. The colon form is therefore matched, anchored to the whole command, only when **EVERY refspec in it is a deletion** — a second refspec that is not itself a deletion disqualifies it, while several deletions together and flags in any position are fine. That last clause is not a convenience: `git push origin :a :b` is the shape this guard was filed over, and an earlier spelling of the anchor refused it, which would have shipped a guard that blocked its own originating command. Among push options, `--mirror` is the one to read twice — it is the only one that deletes remote refs AND delivers commits in a single call, so it is matched by neither deletion leg and stays blocked. The metacharacter condition is what makes the other two checkable: without it a deletion token belonging to a DIFFERENT sub-command exempted the whole string, so `git branch -d x && git push` passed while standing on the default branch — measured, and the reason the condition is spelled as a disqualifier rather than as a parse. Consequences worth knowing before reading a refusal: a deletion whose target is a variable or a substitution is blocked (its target genuinely cannot be read), a `cd <dir> && git push origin --delete x` prefix is blocked, and so is a deletion whose unrelated prose mentions the default branch. A refusal is therefore NOT evidence that the command would have pushed a commit
- PreToolUse(Bash) — `auto-stage-learnings`: stages `ai-docs/learnings.md` **and** the `ai-docs/learnings/` directory on `git commit` (two independent `git status` probes, so a first-write untracked per-branch file is staged too) **[guarded]**
- PreToolUse(Bash) — `co-authored-by`: blocks a `Co-Authored-By` trailer in a `git commit` message (`-m` string or `-F` file) **[guarded]**
- PreToolUse(Bash) — `diff-range-guard`: warns when a gate is built on `git diff <base>...HEAD` on a branch with no commits yet (empty diff at rc=0 → silent pass); points at `git diff <base>` for the working-tree form
- PreToolUse(Bash) — `config-search-gate`: blocks a content search whose file filter can match an ASK-gated deployed-config file. **The gated class is read from the project, never carried here** — the `Deployed-config globs` line of its `ai-docs/context.md`; no declaration, or `none`, means silence rather than a class the guard invented. Two arms over that class: an include-family filter naming it, and an operand naming a file of that name **that exists**. An explicit exclusion, glob or negated-glob, is the way past. The existence test is load-bearing — the arm it replaced matched the name anywhere in the command string, so it refused a search for quoting it in a pattern. Does NOT catch a bare unfiltered search whose pattern matches a config key, nor a filter too wide for any declared glob to appear in, so a clean run is not clearance
- PreToolUse(Bash) — `gate-pipe-guard`: its three patterns live in `${CLAUDE_PLUGIN_ROOT}/hooks/lib/gate-pattern.sh`, which `gate-record` sources too, and it **fails open** when that file is absent, unreadable or leaves the gate pattern empty — the readability guard runs BEFORE the `.`, because a `.` that cannot open its file ends a POSIX shell before a trailing `|| exit 0` is reached; a file present but unparseable is left to the syntax check over tracked shell files. It blocks a gate — a named build / test / lint / format tool, **or a shell interpreter invoking a script file whose basename carries `test` / `check` / `lint` / `verify`**, **or `jq` carrying `-e` / `--exit-status`** (the flag that turns a parse into a verdict, which is what makes a manifest parse a gate — `jq` without it is an ordinary data read and is not matched), which is what makes a suite written in shell a gate rather than an ordinary command; a bare `bash -c …` is not one — whose result is MASKED — piped into `head`/`tail`/`grep`/`jq`/`sed`/`awk`/`wc`/`cut`/`sort`/`uniq`, fused to a trailing `|| echo` / `|| true`, **FOLLOWED across `;` by an `echo`/`printf` banner** (the next command replaces the gate's exit status — note the direction: a banner BEFORE a single gate masks nothing, because the gate is last, and is deliberately not matched), **joined to a SECOND shell gate with `&&`** (which leaves the first gate's verdict unreadable, and lets one legitimate non-zero truncate the rest of the chain). **That leg matches on its OWN pattern, not on the gate set above, and the difference runs both ways** — read it before concluding a conjunction is untouched: it requires a shell interpreter on BOTH sides, either carrying `-n` or running any `*.sh` / `*.bash` path, so it is WIDER than the gate set on the shell side (`bash -n a.sh && bash b.sh` is refused although neither side is a gate for any other leg — that spelling is the recorded incident this leg exists for) and NARROWER overall, since it admits no named build or test tool at all and therefore collides with no package-manager idiom. A conjunction of plain READS stays invisible by construction, which keeps that check with the author. Also, **redirected into `/dev/null`** (which discards the line naming WHICH assertion failed, so even a correct rc leaves nothing to act on), or **run inside a `for` / `while` loop** (which exits with the LAST iteration's status, erasing every earlier failure). The loop leg fires only when the loop BODY invokes a **named build / test / lint / format tool or a shell interpreter**, so a loop over `grep` / `awk` / `realpath` passes. **That is narrower than the rule on purpose, and a pass is not clearance:** `${CLAUDE_PLUGIN_ROOT}/docs/agents-method.md` § Tooling counts **search** among the gates, and blocking every loop containing a `grep` would be intolerable, so the hook deliberately under-approximates. The rule still binds on the construct. **A gate whose path arrives through a VARIABLE or a glob is invisible to this hook by construction** — no guard that matches the command string can see it — so that construct check stays with the author. Carve-outs pass: a `cd <dir> &&` prefix, a `[ -n … ] &&` guard that does not swallow the rc, and any chain inside a hook or checked-in `.sh`. **The gate match is anchored at COMMAND POSITION** (start of string, or after `;` `&` `|` `(` `` ` ``), so a gate name inside a search pattern — the project's own propagation sweep — is not a gate invocation and is not blocked. Newlines are normalised to `;` before matching, so a gate piped across a line break is still caught, and **redirections (`2>&1`, `&>`) are normalised away**, so the commonest spelling of a piped gate no longer slips past the `&` the gap cannot cross. There is NO heredoc opt-out: prose that quotes a piped gate at the start of a line is blocked like any other, and the remedy is the `Edit` / `Write` tools per `${CLAUDE_PLUGIN_ROOT}/docs/workflow.md § Hook false-positive guard`
- PreToolUse(*) — `loop-index`: appends one line per tool call to a per-session ledger (`~/.claude/harness/loops/<session_id>.jsonl`) and, when the SAME `hash(tool + arguments)` has already run within the last `HARNESS_LOOP_TAIL` **CALLS** (default 20), returns `permissionDecision: "ask"` with the count. **The unit is load-bearing and the word "steps" is retired from these messages:** the window is a count of `kind: "call"` ROWS, bound inside `${CLAUDE_PLUGIN_ROOT}/hooks/lib/loop-window.awk`, where the shell can only bound a tail by LINES — and once `loop-result` began writing a row per call, a 20-line tail was roughly 8 calls while the message still said 20. The agent is now told the span actually counted plus the call being judged, never the setting; the verdict row keeps the setting under `window` and names its unit in `window_unit`, because rows written before this change counted lines and nothing in the number separates them. **The intervening-edits filter is CONDITIONAL on the outcome**, and that is not a nicety: for calls that succeeded, a write between the repeats means the world changed and the finding is dismissed; for calls that FAILED, the edit means an attempt was made and the call failed again — the fix-break cycle, where dismissing it is how the commonest logical loop stayed invisible. Two prior failures fire as `error-retry`; three occurrences fire as `loop`. Both numbers mirror `${CLAUDE_PLUGIN_ROOT}/scripts/session-events.sh` (`retry_min: 2` against `minrep: 3`), which applies the same split per signature and always did — the live index diverged from it until GH-69. The key is the **hash alone** and `agent_id` is a field beside it — putting the agent in the key would stop the same hash from two agents matching, which is the fan-out case (N siblings each doing one identical call) that no per-agent view can see. **That arm fires on a ledger this build writes:** `agent_id` is taken straight from the PreToolUse payload, which carries it on a call made inside a subagent and omits it on the main agent's own calls, so an omission stores `main` and a malformed value degrades to `main` rather than dropping the row. **That degradation is silent by construction and the `agent-mark` row below is the only thing that makes it visible** — a stored `main` is indistinguishable from a genuine main-agent call, which is how ten of twelve field ledgers recorded every subagent as `main` with every count beside it correct. The stored `transcript` pointer is the subagent's own file, derived from the parent path the payload reports plus that id, and it is stored whether or not the file has been written yet. `${CLAUDE_PLUGIN_ROOT}/scripts/loop-metrics.sh --for` still recovers attribution at read time by locating each id in the session's transcripts, and now compares the two records: ledgers written by earlier builds stored one id for everything, and `attribution.agreement` is what separates those from a live disagreement. The ledger is an **index, not a copy**: it stores `tool_use_id` and the transcript path, so detail is one join away and no argument content is duplicated; `transcript` is per entry because a subagent writes its own file. The fingerprint is the same djb2 as `${CLAUDE_PLUGIN_ROOT}/scripts/session-events.sh`, and the two must not drift. **`ask` routes into the normal permission flow, so an already-allow-listed command can pass through without a prompt** — the stderr line is the half that always lands. Unguarded (a loop is never project-specific); **every failure path exits 0, unconditionally, so it can never cost a tool call — and `exit 0` is the absolute half of that contract while silence never was.** Silence is the DEFAULT, not the guarantee: the one deliberate exception is an unwritable ledger, reported once per session on stderr, per the ledger-write bullet below
- PreToolUse(Edit|Write) — `propagation-rule-reminder`: advisory nudge on an edit to a Propagation Rule sync-group member. Thirteen arms, each anchored at the PROJECT ROOT: `AGENTS.md`, `CLAUDE.md`, `CLAUDE.local.md`, `agents/*.md`, `rules/*.md`, `skills/*.md`, `skills/*.sh`, `.claude/skills/*/SKILL.md`, `docs/*.md`, `scripts/*.sh`, `scripts/*.py`, `ai-docs/learnings/README.md`, `ai-docs/context.md`. **The project-local skills arm is spelled `*/SKILL.md` and not `*.md` on purpose:** it exists to restore exactly the class the pre-anchoring arms matched, and `*.md` would additionally admit `.claude/skills/<name>/reference.md` and `.claude/skills/notes.md`, which they never did. A sibling project's `.claude/skills/<name>/SKILL.md` is now silent where the unanchored form fired. `.claude/agents/*.md` is a recorded bounded gap on the same reasoning — restoring a regression is in scope, widening past it is not. **Both the anchor and the incoming path are normalised to physical absolute form before matching**, because the arms are GLOB PATTERNS and not paths: a trailing slash, a relative spelling, or a symlinked prefix each silences every arm, and where `/tmp` links to `private/tmp` the anchor and the payload can name one directory and share no prefix at all. Sharing an input with the guard is not sharing a contract — the guard uses the same value as a PATH, which tolerates every spelling that still resolves. **The root anchor is what bounds the false positives:** an unanchored `*/agents/*.md` fires on `my-agents/` and on `node_modules/`, and the leading `*/` never held that line. It requires `CLAUDE_PROJECT_DIR` to BE the project root — a subdirectory is a valid absolute directory, just the wrong one — so that case is a documented invocation condition, not a fixed defect. A write into a not-yet-existing directory cannot be normalised and falls back to the raw path: it still fires whenever that path is already physical-absolute, and otherwise fails SILENT rather than false-positive. An anchor that resolves to no directory emits its own diagnostic instead of going quiet, behind the `[guarded]` prefix which no-ops on that same anchor first. `ai-docs/learnings/<username>-<branch>.md` is deliberately NOT a member: § Learning Log Boundary rule 2 forbids the follow-on instruction-file edits the reminder asks for, so firing there would advise a rule violation **[guarded]**
- PreToolUse(Edit|Write) — `archive-protection-reminder`: advisory nudge when a write ADDS a `### ` header to `ai-docs/learnings.md`, pointing at `ai-docs/learnings/<username>-<branch>.md`. Counts headers before vs after, so a field-only edit and a whole-file rewrite stay silent. Never blocks (`exit 0`) — the `/improve` fold passes through
- PreToolUse(Skill) — `skill-gate`: decides a gated skill by WHO IS ASKING. `deny` with a reason when `agent_id` is present, `ask` when it is absent, silence for every other skill and tool. The discriminator is the payload field the hooks reference describes as present "only when the hook fires inside a subagent call", and it is **measured on this build** — a probe subagent recorded a real `agent_id` and `agent_type` while the main thread records neither — because a gate resting on a field that never arrives is a gate that cannot fail. The gated set is DATA, not logic: `HARNESS_SKILL_GATE` holds a space-separated list (default `task`), and a name is matched after the plugin prefix is stripped, so `task` and `harness:task` are one entry rather than two. This expresses a posture no frontmatter field can: `disable-model-invocation` means "never by the model, with or without the user present", while this means "the main agent may propose it, the user confirms, a subagent may not start it". **Two consequences worth stating rather than discovering.** The refusal also forbids reproducing the workflow by hand, which is the route a blocked agent otherwise takes. And the payload carries nothing that separates a skill the USER typed from one the model proposed, so a user-typed `/task` is confirmed too — inherent to the mechanism, not a defect in it. **Both decisions are defaults rather than guarantees, and for different reasons.** It fails OPEN, like every jq-dependent hook here: absent `jq`, malformed input or an unreadable field all yield silence at rc 0, so the deny is a strong default and not a wall. And the `ask` carries the same caveat the bullet above records for `loop-index` — it routes into the normal permission flow, so an allow-list entry covering the `Skill` tool would let it through unprompted. No such entry ships in this repo's settings or in the scaffolded template, and `defaultMode` is unset in both, so the prompt does fire today; a consumer who allow-lists `Skill` silently converts the confirmation into a pass. Unguarded — the gated skills ship with the plugin, so the gate is never project-specific
- PostToolUse(Write|Edit) — `learnings-append-check`: warns when a new Learning Log entry did not land last in its file
- PostToolUse(Write|Edit) — `sh-syntax-check`: runs `bash -n` on a written `*.sh` / `*.bash` file and BLOCKS (`exit 2`) when it no longer parses, naming the offending line and the commonest cause — an apostrophe inside a single-quoted region, which closes the string so the shell re-parses the remainder and the reported line is far from the real one. Unguarded, like `gate-pipe-guard`: a shell syntax error is never project-specific. Silent for any other extension and for a path that does not exist
- PostToolUse(*), PostToolUseFailure(*) — `loop-result`: appends a `kind: "result"` row keyed by `tool_use_id` recording whether the call succeeded. **The event name is the answer, not a field**: `PostToolUse` fires after a success and `PostToolUseFailure` after a failure, so nothing parses a tool response — whose shape differs per tool and would drift silently. Appends rather than amending the call row: the ledger is append-only by contract, an in-place edit would race the next `PreToolUse`, and a reader that joins is cheaper than a writer that seeks. **This is what makes the fix-break cycle visible** — without an outcome the index could not tell a failing repeat from a succeeding one, so it applied the intervening-edits filter to both and dismissed `test → edit → test → edit → test` at every round. Unguarded
- PostToolUse(Bash), PostToolUseFailure(Bash) — `gate-record`: appends one `kind: "gate"` row per covered gate in a Bash command — the shared gate pattern, or a checked-in script whose path carries `test` / `check` / `lint` / `verify` executed directly — stamped with the tree digest, and tells the calling agent through `additionalContext` one line per gate: the gate, the exit status, the digest. A `repeat` or `contradiction` against any earlier gate row of the session, any agent, adds a sentence naming the earlier command. **The line reaches the calling agent's own context in the main thread and in a subagent alike, after a zero exit (`PostToolUse`) and a non-zero one (`PostToolUseFailure`)** — observed on the installed 0.1.53 build, including a subagent's repeat against a main-thread run; the row, which carries the `agent_id`, stays the durable record. **It never blocks and always exits 0.** Identity survives a `cd`, an assignment prefix, a redirect and an absolute spelling; redirect targets are never arguments. **The verdict is attributed only where the exit status allows** — the last segment after `;` or a lone `&`, or alone, the last of a failing `&&` run with no earlier gate in it, every gate of an `&&` chain that exits zero — and is `null` otherwise, including for a gate backgrounded by a lone `&`, even when it stands alone. **Residue:** a gate inside a command substitution or a heredoc is not seen, a failing non-gate `&&` prefix is recorded as the gate's failure, and a gate that reads an ignored file it is not handed by name is keyed on the tree digest alone. Row contract: [`${CLAUDE_PLUGIN_ROOT}/docs/loop-ledger.md`](${CLAUDE_PLUGIN_ROOT}/docs/loop-ledger.md#the-loop-ledger)
- Stop, SubagentStop — `loop-verdict`: the COARSE stage of the cascade (exact hash → coarse hash → model → deep analysis). Writes a `kind: "turn"` marker on every stop — the ledger has no turn index because `PreToolUse` does not know one, and `Stop` IS the turn boundary — then fires when ONE `bin` repeats `min_bin_repeats` times **within that turn**. The bin comes from `${CLAUDE_PLUGIN_ROOT}/scripts/bin-of.jq`. **The gate is deliberately not a tier-1 signal**: tier 1 fires only on byte-identity, so gating on it would confine this stage to the class tier 1 already caught. **Its first design did not discriminate and was replaced from measurement:** counting DISTINCT fingerprints and requiring one tool to dominate fired on healthy work every time, because ordinary varied work is also "all fingerprints distinct", and in a shell-driven session one tool is ~98% of calls so concentration is vacuous. Coarse repeats within a turn gave a spread (11 / 5 / 4 / 3 / 2) where both older figures were identical for every turn. **The model stage is OFF by default** (`HARNESS_T3_MODEL`); when on it writes a separate `tier: 3` verdict and takes its reason from the FIRST line of the answer. That row also records `flagged_calls` and `unresolved_calls` — how many calls the stage was asked to judge and how many of those yielded no transcript text, so a reader can weigh a verdict by the evidence it rested on; a stored transcript that exists without the call's `tool_use_id` in it counts as unresolved exactly as an absent file does. **It never blocks** — a `Stop` hook returning exit 2 forces the conversation to continue, which is the failure this detector exists to catch. Turn scoping makes re-judging impossible by construction. Absent `claude`, a failed call or an unparseable answer all end it silently. Unguarded; thresholds are a hypothesis from one session and every verdict records the value it fired under. **All three of its ledger writes go through `${CLAUDE_PLUGIN_ROOT}/hooks/lib/ledger-write.sh`**, like tier 1's — but note the trigger differs: tier 1 fails when the ledger DIRECTORY is unwritable (the file does not exist yet, so the open fails), while this stage fails when the FILE is unwritable, since `[ -s "$ledger" ]` tests existence and size and never writability. Narrower trigger, same mechanism, and once per TURN rather than once per call
- SubagentStart — `loop-agent-mark`: appends one `kind: "agent-mark"` row per subagent spawn, carrying `agent_id` and `agent_type`, into the same per-session ledger (`SubagentStart` delivers the PARENT `session_id`, which is the key `loop-index` uses, so the mark lands in the file the call rows are in — measured, not assumed). **It is a CANARY and not a second source of attribution**, which is the distinction that decides what may be built on it: `PreToolUse` already supplies a real `agent_id` on the current build, so this improves attribution by nothing at all. What it buys is that "N subagents started, zero non-`main` call rows" becomes a self-contradiction detectable from the ledger alone, where today the degradation at `loop-index`'s `agent_id` read is indistinguishable from a genuine main-agent call. **It needs a COUNT of starts, not an identity, and no reader may join an `agent-mark` row to a `call` row** — that join is read-time attribution, which `loop-metrics.sh --for` already does by the only honest route, a transcript scan. **It closes one direction only:** zero recorded starts cannot separate "no subagent ran" from "this hook is not firing", and both readers print that bound rather than implying coverage they do not have. The event structurally **cannot block a spawn** — its `hookSpecificOutput` carries only `additionalContext`, with no `permissionDecision` — but a non-zero exit still becomes a `hook_blocking_error` attachment, so the exit-0 discipline binds exactly as it does on the other ledger writers — including their one exception. **The script may not be called `subagent-start.sh`**: a hook command must not name itself with a reserved event-name word from §3b, and that is the forbidden spelling. Unguarded; **every failure path exits 0, unconditionally — but silence is the default rather than the guarantee**, the unwritable ledger being the one deliberate exception, per the ledger-write bullet below
