### 2026-10-09 — testing — a table whose every row agrees with ground truth is evidence about those rows and nothing else
**What happened:** Across four review rounds on one branch, every defect found was in the row SET and not once in a verdict. The structural suite was `32 ok, 0 failed` and the hook suite went 167 → 184 → 196 → 219 assertions, all green, at every single step — while the open findings included a guard that permitted `git branch -d x && git push` from the default branch and, later, one that permitted `git push origin HEAD :feature-x`, measured against a real bare remote as `- [deleted] feature-x` plus `6c27cec..11d6751  HEAD -> main`. The sharpest instance was round 3's: the missing rows sat inside the very leg I had written to price the new restriction's cost, whose own comment said it existed to check the narrowing "must not cost the real colon deletions" — and it priced only single-refspec costs, which is exactly why a pattern refusing every multi-deletion form shipped and passed 196 assertions.
**Rule:** A green suite licenses one sentence: "every case I thought of behaves as I expected." It licenses nothing about the cases absent from it, and the absent ones are not random — they are the ones the author's model of the change does not contain. **The author who adds a narrowing is the one least likely to write the row that measures what the narrowing costs**, because the cost rows are derived from the same model as the narrowing. So when a change RESTRICTS something, the cost rows are the deliverable, not the proof rows: enumerate the shapes that must still pass before touching the predicate, and take that enumeration from the issue's own originating example, which is the one shape a regression cannot be allowed to hit. Here the originating command of the issue — deleting two branches at once — was the shape the fix refused.
**Kind:** correction
**Escalated?** no

### 2026-10-09 — process — "it was measured" does not transfer; a citation inherits the row set, not the authority
**What happened:** A reviewer handed me a replacement regex with "checked against 13 strings", and I adopted it verbatim, telling it so and giving that measurement as my reason for not composing my own. It shipped a regression refusing six real deletion idioms, including the one the issue was filed over. The 13 strings were a real measurement and the pattern was correct for all 13; what was short was the row set, and that is precisely what "measured" conceals when the number travels without the list. I had written the general form of this lesson in the same session, about my own tables, and then failed its transitive case.
**Rule:** When adopting an artefact on the strength of someone else's verification, the thing to ask for is the LIST, never the count — and the question to ask of the list is which shapes it omits, not whether its members pass. A count is a claim about effort; a list is a claim about coverage, and only the second is checkable. Where the artefact restricts something, re-derive the must-still-pass set yourself from the requirement rather than from the handed-over verification, because the author of a narrowing and the author of its verification share a blind spot by construction. `${CLAUDE_PLUGIN_ROOT}/docs/workflow.md` § Relaying a subagent's conclusion already says a correct citation certifies the quote and not the inference; this is the same rule for a measurement — it certifies the rows and not the coverage.
**Kind:** correction
**Escalated?** no

### 2026-10-09 — tooling — five instrument defects in one task, each of which would have read as a result; and tolerating a known one is a separate failure from having it
**What happened:** Across one task, two agents produced five defective measuring instruments. Mine: a probe comparator that compared a padded `pass ` against `pass`, so nine rows that agreed with ground truth printed as mismatches; and a git fixture that pushed its branch without `-u`, so no upstream existed, `git branch -d` compared against HEAD alone, and the probe reported that a correct review finding did not reproduce. The reviewer's: a script path that resolved to nothing after a `cd`, so twenty rows reported BLOCK on rc=127; the identical `pass ` padding; and then the same padding a third time, which it read past rather than fixed. Every one of the five produced output shaped exactly like a finding. The fixture one is the worst of mine, because its false result pointed AWAY from a real defect and I came within one step of reporting that the reviewer was wrong.
**Rule:** An instrument gets a positive control before its output is read as evidence — a row whose answer is known independently, in BOTH directions, so a comparator that never matches and one that always matches are both visible. For a fixture the control is the production spelling: a fixture that differs from production in any field the code under test READS is not a fixture for that code, and the divergence shows up as a clean, confident, wrong answer rather than as an error. And when an instrument defect is already known, fixing it comes BEFORE reading the output again: reading past a known padding bug is not a shortcut but a decision to trust an instrument you have just established is lying, and it is the habit rather than the bug that will cost the next measurement.
**Kind:** correction
**Escalated?** no

### 2026-10-09 — tooling — the "guard matcher wider or narrower than its rule" class reached five occurrences
**What happened:** Counting only this session: the gate guard's name list omitted the manifest-parse gate; its banner leg refused a banner before a single gate, which can mask nothing; `branch-protection` refused a branch deletion, which pushes nothing to the default branch; my own fix then exempted any command carrying a stray deletion token, including a real push; and my second fix refused every multi-refspec deletion. Three of the five were introduced while fixing the other two. Each was invisible to every gate in the repository, which is what `docs/propagation.md` already says about drift between a matcher and the rule beside it.
**Rule:** Before editing a guard's matcher, write down the harm it exists to prevent and the set of commands that can cause that harm — then check the matcher against both directions of that set, not against the examples already in the file. A matcher narrower than its rule under-approximates on purpose and its silence is not clearance; a matcher wider than its rule refuses work that cannot cause the harm, and that refusal is read as a rule by whoever hits it. Both directions need a row, and a guard edit that adds only "it now blocks X" rows has measured half the change. This entry exists to be counted: the class is past the escalation threshold, and the escalation decision belongs to `/improve`, not to the branch that noticed.
**Kind:** correction
**Escalated?** no
